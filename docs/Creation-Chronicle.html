0. CHRONICLE CONTRACT — Cara membaca rekam sejarah ini

Dokumen ini dibuat sebagai Creation Chronicle: catatan naratif mengenai bagaimana PERNAH dirancang, dibentuk, dan dikembangkan sampai milestone yang sedang berjalan.

Dokumen ini bukan pengganti percakapan asli. Arsip percakapan asli tetap menjadi primary record. Chronicle ini adalah dokumen turunan yang merangkum perjalanan tersebut agar lebih mudah dibaca manusia.

Karena tidak semua percakapan historis tersedia sebagai dokumen terpisah di workspace saat chronicle ini dibuat, bagian yang tidak dapat diverifikasi dari artefak yang tersedia tidak diperlakukan sebagai fakta pasti. Jika tanggal atau detail awal tidak tersedia, chronicle menyatakannya sebagai tidak terverifikasi daripada mengarang.

Batas penting: dokumen ini mencatat rekam jejak perancangan dan pengembangan yang tersedia. Ia tidak dengan sendirinya merupakan penetapan hukum mengenai kepemilikan, hak cipta, atau prioritas hukum.

Kontrak Chronicle

  • Peran: Chronicle adalah lapisan naratif/historis yang merangkum perjalanan project agar mudah dipahami manusia.
  • Primary record: Percakapan asli dan artefak sumber tetap menjadi record utama; Chronicle tidak menggantikannya.
  • Source discipline: Klaim historis harus dapat ditelusuri ke percakapan atau artefak yang tersedia. Jika tidak terverifikasi, nyatakan sebagai tidak terverifikasi.
  • Chronology: Urutan milestone mengikuti urutan historis release/keputusan, bukan urutan saat bagian ditulis ulang.
  • Current state: Status terbaru ditulis sebagai current documented state; snapshot lama diberi label historical snapshot.
  • Separation: CHANGELOG mencatat perubahan; Chronicle menjelaskan perjalanan, konteks, dan alasan penting tanpa menjadi source of truth implementasi.
  • Preservation: Refactor visual boleh mengubah presentasi, tetapi tidak boleh menghapus fakta historis yang sudah tercatat tanpa keputusan eksplisit.

1. THE BEGINNING --- Sebuah gagasan tentang memory yang durable

PERNAH lahir dari gagasan bahwa percakapan dengan AI tidak seharusnya menjadi satu-satunya tempat di mana konteks kehidupan seseorang tersimpan.

Gagasan dasarnya kemudian dikonsolidasikan menjadi:

PERNAH = Personal Memory & Life Context System

Arah produknya bukan sekadar membuat chatbot yang bisa menjawab pertanyaan. PERNAH dirancang sebagai memory/life-context engine yang dapat menerima informasi kehidupan sehari-hari, memahami konteksnya, menyimpannya dalam bentuk canonical, lalu mengambilnya kembali ketika dibutuhkan.

Salah satu prinsip filosofis yang menjadi dasar proyek:

"PERNAH sendiri harus punya memory yang lebih durable daripada chat tempat kita membangunnya."

Dari sini, fokus proyek bergeser dari sekadar chat with AI menjadi pembangunan sebuah external memory system.

3. THE CORE PRINCIPLE --- Canonical memory harus independen

Salah satu keputusan arsitektur paling penting adalah pemisahan antara canonical data dan derived data.

Canonical data

Data yang menjadi sumber kebenaran utama:

  • Memory
  • Entity
  • Event
  • Relationship
  • Temporal history
  • Commitment
  • Decision
  • Transaction
  • Physical Object
  • Location
  • Source
  • Confidence

Derived data

Data yang boleh dibuat ulang:

  • Search index
  • Embeddings
  • AI summaries
  • Semantic index
  • Cached answers
  • Relationship suggestions
  • Statistics

Implikasinya sangat penting:

AI provider bukan source of truth.

Jika provider AI berubah, mati, atau tidak digunakan, canonical memory PERNAH tetap harus aman dan usable.

4. LOCAL-FIRST

PERNAH kemudian mengambil arah local-first.

Prinsip yang dipilih:

  • canonical data berada secara lokal;
  • online backup bersifat opsional;
  • backup online, jika digunakan, diarahkan untuk terenkripsi;
  • canonical data harus portable;
  • data harus dapat diekspor dan diimpor;
  • perubahan historis tidak boleh dihancurkan secara destruktif;
  • derived data harus dapat direbuild.

Arsitektur storage yang dituju:

Local canonical data
        │
        ├── Retrieval / Search
        ├── Timeline
        ├── Derived indexes
        └── Optional encrypted backup

Dengan demikian, keberadaan layanan online tidak menjadi syarat bagi identitas canonical memory.

5. TEMPORAL MEMORY --- Memory tidak boleh kehilangan sejarah

PERNAH tidak dirancang sebagai database yang hanya menyimpan "nilai terakhir".

Contoh konsep:

Passport
2026-10-05 → laci meja
2027-03-12 → safe
2028-01-08 → lemari dokumen

Jika user bertanya:

"Terakhir passport gue di mana?"

sistem dapat mengambil state valid terbaru.

Tetapi jika user bertanya tentang sejarahnya, state sebelumnya tetap tersedia.

Prinsipnya:

Informasi yang berubah membentuk history, bukan sekadar overwrite.

Hal ini kemudian menjadi bagian penting dari model temporal PERNAH.

6. CANONICAL DATA MODEL

Model logis PERNAH kemudian mendefinisikan beberapa jenis record utama:

Memory

Representasi informasi yang ditangkap PERNAH.

Entity

Sesuatu yang dapat dirujuk dan dihubungkan dengan memory lain.

Contoh: - person - object - place - organization - document

Event

Sesuatu yang terjadi pada waktu tertentu.

Relationship

Hubungan antara entity atau record yang memiliki validitas temporal.

Commitment

Janji atau kewajiban dengan action, pihak terkait, deadline, dan status.

Decision

Keputusan dengan pilihan, alasan, waktu, dan konteks.

Transaction

Pergerakan uang yang dapat dikaitkan dengan event, person, kategori, dan konteks.

Physical Object

Barang atau benda yang dapat memiliki state dan location history.

Location

Tempat yang dapat menjadi bagian dari history suatu object atau event.

Source & Confidence

Provenance dan tingkat keyakinan terhadap suatu informasi.

7. PROVENANCE --- "Dari mana memory ini berasal?"

PERNAH tidak hanya menyimpan hasil ekstraksi.

Informasi penting juga harus mempertahankan source/provenance.

Contoh source yang didefinisikan:

  • whatsapp
  • web
  • manual
  • import
  • ai_inference

Confidence digunakan untuk membedakan fakta yang dinyatakan langsung dengan hasil interpretasi atau inference.

Dengan demikian, memory bukan sekadar:

passport = safe

tetapi dapat memiliki konteks seperti:

what was said

8. THE RAHAYU EXAMPLE

Salah satu contoh konseptual yang digunakan untuk menggambarkan kemampuan PERNAH adalah input natural-language seperti:

"Urang geus meli laptop hargana 2 jt tadi isuk"

Target konseptual normalisasinya:

language: Sundanese
intent: record_purchase
entity: laptop
amount: Rp2.000.000
action: purchase
time expression: tadi isuk
original_text: preserved

Kemudian query:

"Urang pernah meli laptop can nya?"

tidak seharusnya hanya dicari sebagai string.

PERNAH diarahkan untuk memahami bahwa query tersebut meminta retrieval terhadap memory pembelian laptop.

Dan dalam contoh relasional, nama Rahayu digunakan sebagai person/entity yang dapat dikaitkan dengan event, transaction, atau memory.

9. GOVERNANCE --- CHECKPOINT lahir

Ketika proyek mulai berkembang, muncul kebutuhan agar development tidak berubah menjadi rangkaian improvisasi tanpa jejak.

Dibentuklah CHECKPOINT sebagai fondasi governance.

CHECKPOINT menetapkan antara lain:

  • AI berperan sebagai co-developer, abstraction architect, technical UX specialist, reviewer/QC, documentarian, dan problem solver;
  • perubahan besar mengikuti prinsip plan first, code later;
  • pekerjaan dibatch berdasarkan file/scope;
  • input/output harus dinormalisasi;
  • testing harus dilakukan pada environment yang valid;
  • refactoring harus menjaga integritas behavior;
  • scope harus dikontrol;
  • terminology harus didokumentasikan;
  • source of truth setiap dokumen harus jelas.

Salah satu prinsip dokumentasi penting:

Planning      → BACKLOG
Implementation→ source code
Testing       → test suite / validation
Current state → STATE
Terminology   → Glosarium
History       → CHANGELOG
Rules         → CHECKPOINT

Dengan ini, proyek memperoleh struktur memori untuk dirinya sendiri.

17. SEMANTIC VERSIONING & RELEASE DISCIPLINE

Seiring artifact berkembang, versioning diperjelas menggunakan Semantic Versioning:

MAJOR.MINOR.PATCH

Maknanya:

  • MAJOR = breaking/incompatible change
  • MINOR = feature atau peningkatan besar yang kompatibel
  • PATCH = bugfix/polish yang kompatibel

Development artifact menggunakan pre-release suffix ketika diperlukan, misalnya:

PERNAH-v0.2.0-dev.4.zip

Prinsip release juga diperjelas:

  • artifact dengan versi yang sama immutable;
  • jangan menggunakan nama artifact ambigu seperti latest;
  • release harus traceable ke source state;
  • schema version dibedakan dari product version;
  • CHANGELOG, STATE, dan artifact harus tetap konsisten.

18. EXACT SEARCH

Tahap berikutnya membawa retrieval dari pencarian umum menuju deterministic exact search.

Flow:

QUERY
  ↓
NORMALIZE
  ↓
EXACT MATCH
  ├─ entity name
  ├─ event type
  ├─ amount/value
  ├─ date/time
  └─ normalized text
  ↓
RANKED RESULT
  ↓
MEMORY RESULT

Target behavior:

"Laptop"

→ exact entity laptop

"Laptop 2 juta"

→ entity + value

"Pembelian laptop"

→ event type + entity

"Laptop yang gue beli kemarin"

→ entity + temporal constraint

Search juga menekankan:

  • exact entity matching;
  • case/whitespace normalization;
  • amount/currency filtering;
  • temporal filtering;
  • duplicate suppression;
  • deterministic ranking;
  • query specificity.

Tujuannya adalah membuat retrieval dapat diprediksi sebelum PERNAH masuk ke semantic/AI search.

19. BROADER TEMPORAL QUERY

Setelah exact search, temporal understanding diperluas.

Query yang ditargetkan mencakup:

  • today / yesterday;
  • this week / last week;
  • this month / last month;
  • this year / last year;
  • explicit date;
  • N days;
  • multi-day windows.

Contoh:

"Urang pernah meli laptop minggu lalu?"

dapat dinormalisasi menjadi:

action: purchase
entity: laptop
occurred_after: beginning of last week
occurred_before: end of last week

Edge case penting juga diperbaiki:

"7 hari terakhir"

tidak boleh dianggap sebagai monetary amount hanya karena mengandung angka.

Tahap ini memperluas retrieval dari sekadar "kemarin" menjadi temporal query yang lebih general.

22. LOCAL BACKUP — MENJAGA CANONICAL STATE

Setelah fondasi retrieval dan continuity layer terbentuk, muncul pertanyaan baru: jika canonical memory adalah source of truth, bagaimana truth tersebut dipertahankan secara independen dari instance database yang sedang berjalan?

Jawaban pada v0.2.0-dev.22 sengaja dibuat kecil dan lokal. Alih-alih membuat format backup baru, PERNAH menggunakan kembali kontrak JSON pernah-canonical-v1 yang sudah ada.

CANONICAL SQLITE
      ↓
Storage.backup()
      ↓
pernah-canonical-v1 JSON
      ↓
Storage.validate_backup()
      ↓
VALID / REJECTED

Milestone ini menetapkan beberapa boundary:

  • backup adalah artifact preservation, bukan cache atau derived index;
  • backup tidak membutuhkan AI provider, cloud service, atau runtime dependency pihak ketiga;
  • serialisasi deterministic untuk canonical state yang sama;
  • validation memeriksa format, schema, struktur tabel/row canonical, nilai canonical, dan integritas relasional;
  • relational validation berjalan di SQLite terisolasi sehingga validasi tidak memutasi source database;
  • restore sengaja dipisahkan sebagai operasi recovery untuk gate berikutnya.

Milestone ini mempertajam prinsip preservation: backup baru berguna sebagai fondasi recovery apabila sistem dapat membuktikan bahwa backup tersebut valid sebelum mempercayainya.

Suite development mencapai 60/60 PASS dengan regression coverage untuk database kosong dan terisi, deterministic output, file malformed, mismatch format/schema, table yang hilang, field tambahan, nilai canonical invalid, foreign key rusak, dan import round-trip.

23. RESTORE WORKFLOW — MEMULIHKAN CANONICAL STATE

Pada v0.2.0-dev.23, preservation memperoleh pasangan yang sebelumnya belum ada: recovery. PERNAH kini tidak hanya dapat menghasilkan dan memvalidasi backup, tetapi juga dapat membangun kembali canonical database dari backup yang sudah dipercaya.

VALIDATED BACKUP
      ↓
temporary SQLite target
      ↓
canonical round-trip equality
      ↓
atomic promotion
      ↓
RECOVERED CANONICAL STATE

Storage.restore() sengaja tidak diperlakukan sebagai merge biasa. Default semantics-nya adalah replacement restore: backup yang valid dibangun terlebih dahulu pada file target sementara, seluruh canonical record dimasukkan dengan foreign-key enforcement, lalu hasil export canonical dibandingkan kembali dengan payload backup.

Hanya setelah pemeriksaan tersebut berhasil, file sementara dipromosikan ke target menggunakan atomic filesystem replacement. Jika backup invalid, relationship rusak, staging gagal, atau path backup dan target sama, operasi ditolak tanpa memutasi target yang sudah ada.

Dengan demikian, dev.23 membentuk continuity loop yang lebih lengkap:

CANONICAL STATE
      ↓ backup
PRESERVED ARTIFACT
      ↓ validate + restore
CANONICAL STATE AGAIN

Suite regression bertambah menjadi 66/66 PASS, termasuk restore database kosong, populated database, replacement terhadap target lama, round-trip equality, invalid backup safety, broken foreign-key safety, dan collision guard.

Milestone ini juga melahirkan kebutuhan editorial yang lebih eksplisit. Creation Chronicle sesi 23–24 diaudit untuk mengembalikan konsistensi bahasa Indonesia tanpa menghapus fakta historis. Dari sini muncul istilah Arsiparis: peran yang menjaga keterlacakan perjalanan project melalui artifact, provenance, changelog, chronicle, dan dokumentasi tanpa menggantikan source of truth.

24. PORTABLE EXPORT/IMPORT + DISASTER RECOVERY

Pada v0.2.0-dev.24, fondasi backup dan restore diperketat menjadi workflow portable yang lebih aman untuk dibawa keluar dari satu instance SQLite. Fokusnya bukan membuat format baru, melainkan memastikan kontrak pernah-canonical-v1 benar-benar dapat diekspor, dibaca kembali, divalidasi, dan digunakan dalam latihan recovery tanpa memperlemah canonical storage.

CANONICAL SQLITE
      ↓
atomic portable export
      ↓
pernah-canonical-v1
      ↓
validate + relational preflight
      ↓
import / restore
      ↓
recovered canonical state
  • Storage.export_json() sekarang menulis melalui file sementara lalu melakukan atomic replacement, sehingga export yang terputus tidak menggantikan artifact valid dengan file parsial;
  • export otomatis membuat parent directory yang belum ada;
  • Storage.import_json() menjadi jalur import file yang memvalidasi canonical structure dan relational integrity sebelum target dimutasi;
  • import_canonical() mendapat relational preflight yang sama, tetapi tetap mempertahankan semantics merge/dedup-oriented;
  • full replacement recovery tetap dipisahkan pada Storage.restore();
  • disaster recovery diuji dalam temporary environment dengan menghapus database live secara terkontrol lalu membangunnya kembali dari backup yang tervalidasi;
  • backup korup diuji sebagai failure path dan tidak boleh memutasi target yang sudah ada.
